# Contributing to Scripture

Thank you for wanting to help. Scripture is a set of visual tools for studying
the Bible, and it gets better every time someone checks a reference, improves
a map or builds a new study. This guide explains what we're making, what we
will and won't accept, and how to get your change in.

## Start here: the text stays as it is

> Ye shall not add unto the word which I command you, neither shall ye diminish
> *ought* from it.
>
> Deuteronomy 4:2

Scripture makes tools for reading the Bible. It does not add to it, take from
it, or speak for it. Please read these three commitments before anything else;
every contribution is reviewed against them.

1. **The text is never changed.** The site shows the King James Version, the
   standard 1769 text, exactly as published. It is generated from
   [eBible.org](https://ebible.org/) by `npm run data:kjv` and guarded by
   tests. Nobody edits it by hand, and no study may paraphrase, abridge,
   modernise or reorder it.
2. **Show, don't teach.** A study shows what is in the text and where: counts,
   distances, sequences, places, connections. It does not argue for a
   doctrine, a denomination's reading, a date for a prophecy, or any
   interpretation. The reader draws the conclusions, with the verses in front
   of them.
3. **Name everything that comes from outside the text.** Maps, dates,
   reconstructions, proposed literary structures and cross references come
   from people, not from the Bible. Each one must be credited where it
   appears (source and licence), described as what it is ("a proposed
   structure", "a traditional location", "an approximate date"), and shown
   beside the verses it depends on. Where careful readers disagree, show the
   alternatives side by side rather than choosing one.

People of many Christian traditions will use these tools. Write labels,
summaries and help text that any of them can read and recognise as fair to the
text, whatever their own convictions.

### What this means in practice

**Welcome:**

- Corrections where a study misquotes, misnumbers or mislabels a verse
- Maps, timelines, family trees and structures, each with a cited source
- A second, credited view where scholars or traditions differ (a disputed
  route, an alternative date, another proposed outline)
- Open datasets with a licence that allows reuse, credited in `docs/data/`
- Accessibility, performance and design improvements
- Fixes to labels that say more than the verses do

**Not accepted:**

- Any change to the wording of the KJV text, its verse numbering, or its
  italics and red letters. If our text differs from the 1769 standard, that
  is a pipeline bug: report it with the reference and the correct reading.
- Commentary, devotional writing, sermons or applications of a passage
- Content that argues for or against a doctrine, a church or a tradition
- Interpretations of prophecy presented as fact
- Text, summaries or "insights" generated by AI and presented as describing
  the Bible
- Data whose licence doesn't allow reuse, or that has no traceable source

If you're not sure whether an idea fits, open an issue and ask before you build
it. The maintainer makes the final call on what belongs in the project, and
will always explain why.

### When a study presents one reading

Some studies show a structure or reading that not everyone holds (for example,
Revelation's mirror shows one proposed chiasm of Revelation). If you disagree
with it, the fix is not to replace it with your reading. Instead, help us make
sure it is credited, clearly labelled as a proposal, and checked against the
text, and suggest the alternative as an additional, credited view.

## Ways to contribute

You don't need to write code.

| I want to… | Do this |
|---|---|
| Report a wrong verse, number, label or place | [Report a mistake](../../issues/new?template=report-a-mistake.yml). Use the **Contribute** button in a study to fill in the study and your exact view. |
| Suggest a new study or an improvement | [Suggest a study](../../issues/new?template=suggest-a-study.yml) |
| Report something broken | [Something is broken](../../issues/new?template=something-is-broken.yml) |
| Fix a bug or build a study | Read on |

Look for issues labelled **good first issue** if you'd like somewhere to start.

## Set up

You need [Node.js](https://nodejs.org) 20.9 or newer (22 recommended) and git.

```bash
git clone https://github.com/<you>/scripturetools.git   # your fork
cd scripturetools
npm install
npm run dev                                        # http://localhost:3000
```

Before you open a pull request, run the same checks as CI:

```bash
npm run lint
npm test
npm run build
npm run typecheck
```

`typecheck` relies on route types that `next build` and `next dev` generate,
so run it after one of them. `next dev` and `next build` can't run at the same
time in this project.

## How the code is organised

Read these before a larger change:

- [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md): the stack and how studies plug in
- [docs/DESIGN.md](docs/DESIGN.md): the design system, including how we write
- [CLAUDE.md](CLAUDE.md): the conventions in short, and the rules for this
  version of Next.js, which differ from older ones

The essentials:

- **Studies** live in `src/studies/<slug>/` and are listed in
  `src/studies/registry.ts`. Their routes in `src/app/studies/<slug>/` stay
  thin.
- **Every study renders inside `StudyShell`**, the shared frame. It gives each
  study its top bar, panels, status bar and **Contribute** menu.
- **Verse text** is rendered with `<VerseText>`, never as raw HTML. It keeps
  the translators' italics, the words of Christ in red and LORD in small
  capitals.
- **Data** in `public/data` is generated by `scripts/data`. Never edit it by
  hand; change the pipeline and regenerate.
- **Book ids** are USFM codes (`GEN`, `PSA`, `JHN`, `REV`). References are
  written `REV 12:9`, `REV 12:9-11`, `REV 12`.
- **Internal links** are built with `src/lib/routes.ts`.
- **Every non-KJV dataset** is credited in `docs/data/` and wherever the
  interface shows it.

### Adding a study

1. Open an issue first and describe what the reader will see and do, which
   books it covers, and where any outside data comes from. Agreeing on the
   idea first saves everyone time.
2. Add an entry to `src/studies/registry.ts` with `status: "planned"`.
3. Build it in `src/studies/<slug>/` inside `StudyShell`, with its own palette
   in `src/studies/palettes.ts`. Keep shareable state in the URL hash.
4. Credit its sources in the study, in `docs/data/<slug>.md`, and in the
   registry's `sources`.
5. Add tests for its data: counts, references that resolve, nothing invented.
6. When it's ready, set `status: "live"` and `released: "YYYY-MM-DD"`, and
   `preview` to the view that pictures it best (for example `view=arcs`).
7. Update the README gallery and `docs/STUDIES.md`: with the site running
   (`npm run build && npm start`), run `npm run docs:shots` for its picture (it also
   refreshes the README's cover),
   then `npm run docs:studies`. A test fails until both are up to date.

## Pull requests

- Keep each pull request to one change, and explain the reason for it.
- Include a screenshot or short recording for anything visible.
- Write commit messages in plain, sentence-case English that says what the
  change does for a reader of the code, for example "Fold the arcs at the
  centre on F".
- Make sure the checks pass. A maintainer will review it, may ask for
  changes, and will merge it when it's ready.

### Using AI tools

You're welcome to use AI coding assistants; this repository includes
instructions for them in `CLAUDE.md` and `AGENTS.md`. You are responsible for
everything you submit. Never let a tool write or alter Bible text, verse
references, summaries of passages or source citations without checking each
one yourself against the text and the source.
